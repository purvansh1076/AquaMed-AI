# AquaMediAI — Known Limitations

This document explicitly lists all verified limitations of the AquaMediAI system. No feature is claimed or implied to work beyond its documented scope.

## 1. Synthetic Data Only

**Scope**: Entire system
- **Limitation**: All water demands, scenarios, model predictions, allocation results, and negotiation outcomes are generated algorithmically from the FAO-56 single-crop-coefficient method. No real farmer water-usage records, field measurements, or meteorological data are used at any point.
- **Impact**: Model metrics (MAE, RMSE, R²) reflect fit to synthetic signals only. They do not guarantee real-world agricultural accuracy.
- **Disclaimer**: Persisted in `evaluation_results.json`, SHAP output panels, and the API `GET /predict` and `GET /explain/{farmer_id}` responses.
- **Mitigation**: None — this is a synthetic-prototype system. Real agronomic validation requires independent field data.

## 2. PostgreSQL / psycopg2 Dependency

**Scope**: API test suite (`tests/test_api.py`) + health endpoint
- **Limitation**: The `database_url` in `config.py` uses `postgresql+psycopg2://`. The `psycopg2-binary` package must be installed for the API test suite to achieve 72/72 pass. Without it, 68 API tests error at engine/module import time. Without a running PostgreSQL instance, the health endpoint reports `"database": "unreachable"`.
- **Impact**: 68 test errors if `psycopg2-binary` not installed; health check reports degraded status.
- **Fix**: `pip install psycopg2-binary` (already declared in `backend/requirements.txt` line 12).
- **Core system**: The 704 backend tests (ML pipeline, LP allocator, negotiation, conflict detector, data generator, farmer agents, explainability) all pass without PostgreSQL or psycopg2.

## 3. Model Artifacts Not Persisted in Repository

**Scope**: ML pipeline (`backend/app/ml/trainer.py`)
- **Limitation**: Trained model artifacts (`xgb_model.joblib`, `rf_model.joblib`, `encoders.joblib`, `evaluation_results.json`) are not checked into the repository. They must be generated by running `run_training_pipeline(n_samples=3000, seed=42)` before inference, prediction, or negotiation can function.
- **Impact**: First-run users must execute the training pipeline before the API endpoints `/predict`, `/allocate`, `/negotiate`, and `/explain/{farmer_id}` work.
- **Mitigation**: Documentation in `docs/SETUP_AND_EXECUTION.md` and `docs/ML_EVALUATION.md` provides the exact command.

## 4. Single-Crop FAO-56 Assumption

**Scope**: Data generator (`backend/app/ml/data_generator.py`), ML features, allocation constraints
- **Limitation**: The synthetic data generator and all downstream components (feature encoders, prediction model, allocation objectives) assume exactly **one crop type per farmer**, using a single crop coefficient K_c. Multi-crop fields, mixed-crop farms, or rotation-based K_c switching are not modeled.
- **Impact**: The system cannot represent farms growing multiple crops simultaneously with individual water budgets per crop. The `kc_value` feature is a single scalar per farmer.
- **Mitigation**: None in this prototype version. A multi-crop extension would require per-crop feature vectors and a modified allocation model.

## 5. No Real-Time Data Integration

**Scope**: ML pipeline, weather parameters
- **Limitation**: All weather inputs (temperature, humidity, wind, radiation → ET₀) are synthetically generated within parameter ranges at data generation time. There is no integration with live weather services (OpenWeather, NOAA, etc.). The `rainfall_mm`, `temperature_celsius`, and `humidity_percent` features are fixed at dataset creation time.
- **Impact**: The system cannot react to real-time weather changes or drought declarations. Scenario types (e.g., `sudden_rainfall`) are pre-programmed signal modifiers, not live observations.
- **Mitigation**: None — this is an academic prototype with synthetic data.

## 6. One Crop Per Farmer / Fixed K_c

**Scope**: Data generator, feature engineering, ML models
- **Limitation**: Each farmer record has exactly one `kc_value` and one `water_demand_m3`. There is no mechanism for growth-stage-varying K_c (e.g., K_c changes from vegetative to flowering stage) within a single farmer instance.
- **Impact**: The model cannot capture the typical FAO-56 practice of updating K_c across the phenological cycle. The `growth_stage_encoded` feature is categorical but not functionally integrated into the K_c lookup.
- **Mitigation**: None in this version.

## 7. Negotiation Max Rounds Limited to 5

**Scope**: Negotiation engine (`backend/app/negotiation/negotiation_types.py`, `negotiation_engine.py`)
- **Limitation**: The default `NegotiationConfig.max_rounds` is 5. Longer negotiations (beyond 5 rounds) are not supported without config modification. Larger farmer groups or more complex scarcity scenarios may not converge within 5 rounds.
- **Impact**: Negotiation may terminate at `MAX_ROUNDS_REACHED` even if an agreement is potentially feasible with more rounds.
- **Mitigation**: Override `max_rounds` via `NegotiationConfig(max_rounds=n)` where n > 5.

## 7. BATNA Protection Overrides All Thresholds

**Scope**: Negotiation response evaluation (`evaluate_farmer_response` in `mediator.py`)
- **Limitation**: If a farmer's utility at a proposed allocation is below their BATNA utility (`utility < batna_utility`), the response is **always** REJECT, regardless of the acceptance_threshold (default 0.65) or min_batna_buffer (default 0.02). This is an absolute rule.
- **Impact**: In severe-shortage scenarios where the WaterAllocator cannot meet even minimum requirements, all farmers may receive utilities below BATNA, causing unanimous REJECT and negotiation termination at `FAILED` or `NO_FEASIBLE_IMPROVEMENT`. This is intentional behavior (BATNA protection) but may appear as "unreasonable" termination to users unfamiliar with the design.
- **Mitigation**: The system explicitly records `is_batna_protected=True` in the response audit trail, and the termination reason explains the BATNA violation.

## 8. Constraint Verification — Minimum Requirements Not Hard

**Scope**: GLOP allocator (`lp_allocator.py`), constraint verification (`verify_constraints`)
- **Limitation**: Hard constraints are H1 (x_i >= 0), H2 (x_i <= max_water_i), H3 (sum x_i <= available_water). Minimum requirement satisfaction (S1) is a **soft constraint**: when Σmin_req > available_water, S1 is converted to a penalty term in the objective function rather than enforced as a hard bound. This means some farmers may receive allocations below their minimum requirement, and this is intentional and verified as valid.
- **Impact**: `minimum_shortfall_m3` may be positive in the output; `constraint_status` may be "minimum_relaxed". This is correct behavior but may confuse users expecting all minima to be met.
- **Mitigation**: The constraint verification report (`ConstraintVerificationResult`) clearly labels which farmers have shortfalls and by how much.

## 9. Jain's Fairness Not Enforced

**Scope**: GLOP allocator objective, negotiation mediator
- **Limitation**: Jain's Fairness Index is computed and reported **post-hoc** as a measurement tool. The LP objective does **not** enforce fairness; it maximizes the weighted utility objective. An unfair allocation (one farmer gets far more than others with similar claims) is mathematically possible if the weights (urgency, crop_sensitivity) differentiate the farmers.
- **Impact**: Fairness score may be low (e.g., 0.3-0.4) in scenarios with highly differentiated urgency/crop_sensitivity weights, even though all hard constraints are satisfied.
- **Mitigation**: Fairness is reported transparently; users can adjust `ObjectiveWeights` to favor more balanced allocations.

## 10. SHAP Values on Synthetic Model Only

**Scope**: Explainability (`backend/app/ml/explainability.py`, `test_explainability.py`)
- **Limitation**: SHAP explanations are computed on the trained XGBoost/RandomForest model, which was itself trained on synthetic data. The feature importance rankings and local SHAP values reflect synthetic-signal patterns, not real agronomic relationships.
- **Impact**: SHAP dashboards in the UI should be labeled "synthetic data only"; users should not infer real-world causal relationships from SHAP values.
- **Mitigation**: Disclaimer string "Based on synthetic data generated via FAO-56 single-crop-coefficient method" is persisted in all SHAP output.

## 11. Frontend-Backend Text Alignment

**Scope**: Full stack (React frontend → FastAPI backend)
- **Limitation**: Some UI error messages and terminology may not exactly match the backend response schemas. While the API contracts are consistent (72/72 API tests pass), the frontend client may display slightly different wording for the same error condition.
- **Impact**: Minor terminology discrepancies between API responses and UI displays.
- **Mitigation**: The frontend API client maps backend error codes to UI-friendly messages; edge cases may differ.

## 12. No Concurrency or Async Support

**Scope**: FastAPI application, SQLAlchemy engine
- **Limitation**: The SQLAlchemy engine is synchronous (not asyncpg + create_async_engine). The `get_db()` dependency uses synchronous session management. Concurrent request throughput is limited by the synchronous model.
- **Impact**: Under high load (many simultaneous negotiation sessions), the system may degrade. Not suitable for production-scale concurrent use without async migration.
- **Mitigation**: The codebase includes a comment in `database.py` acknowledging this and noting the migration path.

## 13. Developer Note: Empty Scenarios and Edge Cases

**Scope**: All modules
- **Limitation**: Various edge cases produce empty or zero-result outputs that are valid but may be surprising:
  - Zero farmers → `WaterAllocator._empty_result()` returns empty allocation
  - Zero available water → `WaterAllocator._zero_water_result()` returns all-zero allocations, solver_status=OPTIMAL
  - Minimum-infeasible scenarios (Σmin_req > available_water) → LP-relaxed objective with penalty; some farmers get below-minimum allocation
  - Negotiation with 1 farmer → may AGREED immediately if utility >= threshold
  - All farmers at max requirement, available_water insufficient → H2 (max) constraints bind; some farmers at max, others at 0
- **Mitigation**: All edge cases are covered by unit tests (704 total); review test output for expected behavior.
